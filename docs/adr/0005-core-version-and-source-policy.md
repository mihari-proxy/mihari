# 三平台统一核心版本与来源规则

2026-09-19 范围复审决定：正常运行期间的更新失败仍自动回滚；daemon 被强杀或机器断电后保留材料、检测未完成更新并阻断不确定启动，由用户主动一键重装 mihomo。重装采用更新前原通道的官方最新版，保留订阅和配置；失败保留备份与阻断，成功验收后才解除阻断。本次不建设完整的跨崩溃自动恢复机制，也不让普通“核心重启”承担事务修复。三平台统一产品行为，保留各自已有保护并补齐本次更新必需的权限／文件身份检查；完整的 Windows／非 root Unix 持续执行前检查体系另行立项。具体取舍与验收边界见[复审记录](../superpowers/plans/2026-09-19-core-scope-reassessment.md)。

2026-09-17 设计访谈已确认：移除 Unix root 核心被固定在 mihomo v1.19.30 的产品限制，Windows、Linux、macOS 统一支持官方 stable/alpha 通道最新版本；本次不增加历史版本选择或自编译、第三方核心导入入口。保留各平台现有权限和文件身份保护，不将解除版本限制等同于删除所有执行校验。

离线安装允许使用包内固定的官方核心，即使它并非当前通道最新版本。核心在线更新由用户主动发起，更新 Mihari 本身不应顺带强制更新 mihomo。

更新准备期间旧核心继续工作。下载、校验、配置验证或重启失败时，保留或恢复旧核心与原通道，并明确报告更新失败；stable 与 alpha 不因失败自动互相切换。如果恢复旧核心也失败，停止自动尝试，保留可恢复文件，明确报告更新与恢复两次失败及其原因，不宣称恢复成功。

2026-09-17 访谈 Q1–Q8 的产品规则已逐项确认，并已按用户要求形成[实施设计](../superpowers/specs/2026-09-17-core-version-and-update-design.md)。具体授权与完成证据见[执行计划](../superpowers/plans/2026-09-17-core-version-and-update-plan.md)；工作区已有部分实现，尚未完成端到端验收。本文的 accepted 状态表示产品与范围决定已获批准，不代表实现已通过验收。

本地既有核心按部署权限、文件身份与运行兼容性接纳，不强制要求官方来源证明或 provenance；包括管理员手动部署的自编译核心。官方来源限制只约束 Mihari 在线下载，不作为本地已有核心的准入条件。执行版本探测本身也属于执行核心，须先完成对应权限和文件身份检查。接纳本地已有核心不意味着新增自定义核心导入入口。

## 在线更新与失败处理

官方提供 SHA-256 摘要时必须校验，摘要不匹配则更新失败。官方未提供摘要时允许从官方 HTTPS 下载，继续执行大小限制、解压安全、候选版本和配置检查，并提示缺少摘要校验。摘要缺失与摘要不匹配是不同结果；不能把下载后自行计算的哈希视为来自官方的独立校验依据。

本次更新使用开始时解析确定的通道发布及制品。下载期间上游发布更新版本，不改变本次目标；完成后由后续检查提示新版本。发现选定制品被替换、消失或校验失败时，本次更新失败并保留旧核心，不悄悄重新选择其他制品。滚动 alpha 同样遵循该规则，不能只凭其固定通道标签认为制品身份不变。

摘要缺失、版本探测及配置检查均不能证明核心完整安全或所有订阅都兼容。接纳本地核心的责任边界是有权部署它的用户或管理员，而不是 Mihari 对其官方来源作保证。

## 验收场景

- 三平台在线 stable/alpha 安装与更新不依赖编译时固定的 mihomo 版本表，检查版本与实际选定目标遵循同一通道规则。
- 本地 v1.19.30、新版或自编译核心不会仅因版本未列入白名单或缺少 provenance 被拒绝；不安全的部署权限及文件身份变化仍被拒绝。
- 离线包内附官方核心可以在离线环境安装，不要求证明它是此刻最新版；更新 Mihari 本身不会顺带强制更新核心。
- 官方摘要存在且匹配时正常继续；摘要不匹配失败；摘要缺失时允许继续并提示，大小与解压限制等其他检查照常生效。
- 更新目标确定后发布新的 stable/alpha，不导致本次操作中途切换目标；检测到目标制品发生变化或消失时失败。
- 下载、配置验证、发布或启动失败时，覆盖旧核心与通道的保留或恢复路径；准备期间旧核心继续工作。
- 更新和恢复均失败时保留两次错误与可恢复文件，停止自动尝试，不跨通道回退或误报成功。
- 使用合成制品、fake core、临时目录和现有隔离平台验证覆盖这些行为；真实核心、订阅和系统服务操作仍需单独授权。

## 背景与替代关系

PR #211 引入 Unix 核心编译信任表；当时的 Unix 布局设计明确将 Windows 保持原状。PR #217 移除 RootConfigPolicy 后保留核心身份校验及固定版本范围。此次决定替代“只有编译表列出的版本才能成为受信核心”的产品约束，采用在线下载限制官方来源、本地部署由有权部署者负责的规则；安全执行的实现由后续设计确定。

官方来源、核心版本、运行兼容性是不同概念：官方新版本可以成为候选，但仍需通过对应平台、配置及运行检查；来源可信不构成所有订阅与配置均兼容的保证。

## 当前平台差异（调查事实）

Windows daemon 未注入 TrustedCore，即使服务以高权限运行也使用普通安装器：stable/alpha 从官方通道查询候选，下载时有上游 digest 才校验 SHA-256；随后检查候选版本及配置，并进行可回滚替换。普通核心启动没有 Unix provenance 路径的逐次来源凭据与二进制身份校验。AIO 构建时的制品校验不能等同于安装后的持续身份保护。

统一后的目标是本文确定的官方在线下载、本地核心接纳和权限/身份保护规则，不要求给 Windows 补一套强制官方来源凭据，也不把 Unix 现有版本白名单继续作为执行资格。
