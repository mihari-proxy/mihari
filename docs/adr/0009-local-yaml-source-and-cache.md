# 本地 YAML 记录来源路径，由 daemon 刷新并使用独立缓存

本地 YAML 与远程 URL 都是 Mihari 配置条目的持久化来源。daemon 按自身操作系统权限从记录路径读取普通文件，支持手动与定时刷新；不做文件 watcher，不要求 CLI/TUI 保持运行。系统模式允许使用 daemon 的高权限读取，不增加来源目录白名单，也不承诺文件对发起请求的用户可读；这是已明确接受的权限边界。

取得的原始 YAML 先校验并保存为独立缓存，再结合 Mihari 管理设置生成运行配置。TUI 参数覆盖不修改源文件或导入缓存；源文件变化仅在成功刷新后影响缓存。直接运行源文件会混淆用户维护内容与 Mihari 参数覆盖，因此不采用该方式。客户端读取再上传内容无法独立支持后台定时刷新，也不采用。

本地与远程新 sub 均先取得内容并校验，完成必要确认后才创建；获取或校验失败不留下条目。这替代原有远程 add 先注册再首次获取的行为，以确保创建前能识别文件依赖并取得同意。后续读取、校验或应用失败保留最后有效缓存和运行配置，使用既有诊断机制向 TUI 反馈实际原因。条目统一展示与切换，但本地来源和远程来源禁止相互转换。具体协议字段及路径格式仍待定稿。

首版只缓存主 YAML，允许其中的本地文件引用并交给 mihomo 原生处理；Mihari 不复制引用文件，不引入多文件资源缓存事务。创建新 sub 时，校验后说明文件依赖、原生监听、外部文件不可用及回滚范围的后果，用户同意才继续；本地与远程来源均适用，仅创建时确认。URL 引用继续由 mihomo 原生下载和管理，HTTP provider 的缓存路径不应误判为外部输入文件引用。

主 YAML 缓存的独立可用性不代表完整资源集可离线使用。引用文件变动可能直接影响 mihomo，不受主 YAML 刷新开关控制；引用文件丢失可能影响运行或重启。选择原生文件引用是在使用便利性与完整资源快照之间的取舍，不能承诺主 YAML 回滚同时恢复外部文件。

非交互 CLI 通过 --allow-file-references 明确接受文件引用后果；检测到引用但没有 flag 时失败并提示提供该 flag。交互 CLI/TUI 使用默认取消的确认；无文件引用不增加确认步骤。

本地 YAML 的相对输入文件引用按主 YAML 本次读取的实际目标所在目录解析，并仅在生成运行配置时改成绝对路径；主 YAML 是符号链接时使用实际目标目录，刷新时重新解析。缓存内容关联其取得时的目录基准，不能在离线使用旧缓存时按已变更链接目标重解释。用户可沿用放在同一目录的配置及引用文件；源 YAML 和主缓存保留原始内容。远程主 YAML 没有对应本地源目录，其引用保持 mihomo 原生工作目录语义。

主 YAML 和引用文件均允许任意路径，不维护来源允许目录列表；核心配置需解除其工作目录范围对引用文件的拒绝。这是明确接受的执行安全边界调整，不能继续宣称本功能保持原有核心安全路径范围。操作系统权限仍然有效，访问失败通过现有诊断机制反馈。具体环境配置需核对实际受支持核心能力。

CLI 保留远程 `sub add NAME URL`，本地使用 `sub add NAME --file PATH`，同类型来源编辑使用 `sub set ID --file PATH`；URL 与文件参数互斥，禁止借编辑入口转换来源类型。

来源复用现有 url 字段，本地路径规范化为 file URI，来源类型由 scheme 推导；不另存冗余类型与文件路径。缓存另外关联取得主 YAML 时的实际目录，与内容共同提交和回滚。这区分“下次刷新的位置”与“已有内容的相对引用基准”，避免编辑来源或切换符号链接后错误解释旧缓存。远程条目省略新增目录元数据；包含本地条目的 catalog 不保证旧版本可读，降级需移除本地条目或恢复兼容备份。
