## 2. 已有本地实现

已批准的基本方案是 macOS installed launchd 服务与 mihomo 共享 daemon PGID；Linux、Windows 和 macOS 前台保持原有分组。下列代码已在 worktree，但仍需与补充机制整合：

- `cmd/mihari`、`internal/cli`、`internal/app/runtime.go`：隐藏 --launchd-process-group 标记、PID==PGID 检查及显式 ShareProcessGroup 装配。该标记未进入已提交 HEAD、未发布。
- `internal/supervisor`：Darwin 共享模式子进程不另建 PGID；仅向实际持有的 core leader 信号。kqueue NOTE_EXIT 不回收地观察退出，先关闭信号入口再 Cmd.Wait，避免回收后 PID 复用。后代不清空时禁止重启、Maintain 和后台工作绕过。
- `internal/platform/process_group*`：CGO0 Darwin libSystem/汇编桥；固定两 PID 槽的 proc_listpids 判断共享组是否还有其他成员。不能改回 Darwin waitid WNOWAIT；之前核对 Go 的 Darwin 等待限制后选择了 kqueue。
- `internal/service/definition*launchd*`、`definition_darwin*`：实际 argv、boot/PID/start 身份与 Group token；native bootout 后被动查询整个组退出，只认明确不存在，不能向历史 PGID 补发 TERM/KILL。
- `internal/app/install_recovery.go`、`install_native_session_unix.go`：绑定持久旧身份、避免 Inspect 清空依据；completed journal 或 Start/RestoreStart 后的新 generation 没有旧证明时拒绝。正是这个保守拒绝暴露了需要补充登记机制的可用性缺口。
- `internal/integration/unix_security_launchd_*_darwin_test.go` 与 `scripts/test`：hosted-only 真实 launchd fixture，覆盖共享组、忽略 TERM 的后代和独立 cleanup ledger。未知 PGID=0 不能清理成功；Python required helper 清单和 always cleanup 一同校验。

## 3. 补充机制仍未实现

[补充设计](../specs/2026-09-08-darwin-runtime-group-handoff-addendum.md) 磁盘版本仍为 **R3**。拟增加：

- 固定全局 B/launchd-runtime/state.json，generation 只有 null 或 {boot_id,pid,start}。
- 一把永久 start.lock；installer B→P→gate→data→endpoint，daemon gate→data→endpoint。
- 只有 daemon 发布非空记录；installer 原子初始化或确认整组退出后写 null，删除了代登记方案。
- 登记必须先于 credential、业务恢复及任何 managed child；installer 专用 RunInheritedValidation 不进入 gate。
- 原子发布完整初始化目录，严格区分首次初始化与已入场记录损坏；legacy 不可借 null 绕过旧进程检查。
- source 回滚、target 启动及重放统一交接，等待 Ready 前释放 data/E 和 gate，后续写数据必须重新停机。

这些持久文件、gate 和完整 source 启动权限均没有实现。不要因已有 ShareProcessGroup 参数就把当前 binary 当成已支持完整登记合同。

## 4. Important：必须先修补设计的实际调用链

R2 的独立审查发现 source 回滚后的持续启动权缺失；R3 补充了 pending RestoreStart 与 source+complete 的条件，reviewer 曾认为设计可实现。**这只是历史设计审查结论。用户要求再次核查后，发现 R3 尚未把这些条件接到全部实际检查层。最后一次“修复设计”被用户切换为交接，尚未修改 R3，未产出 R4。**

已核实的现有代码：

1. `internal/app/install_recovery.go:160` 恢复 OldDefinition，只有 old.Running 才 Start；最后写 source+complete。
2. `internal/app/startup_gate.go:19` 先拒绝 pending，再只接受 target；`startup_gate_unix.go` 只比对目标 CandidateHash。合法 source 当次启动与后续重启均缺专门入口。
3. `cmd/mihari/unix_layout.go:115` 第二次检查要求 phase 与第一次完全相等。合法 intent/done/complete 推进可能因此被当作实例变更；应重新核验同一授权对象，不应仅比 phase 字符串。
4. 只修改入口仍不够：`cmd/mihari/main.go:482`、`internal/daemon/activation.go:11`、`internal/app/runtime.go:88`、`internal/runtime/settings.go:148` 都依据原 phase 拒绝 pending 的业务构建、Manager mutation 或 worker。R3 没有交代这些层如何接收合法 source 恢复授权。
5. `TestNativeInstallBoundary_SourceRecoveryRetriesAfterRestore` 使用 fake manager，最终检查 manager.running；没有真的启动 daemon 或经过上述检查，不能证明恢复后的服务可用。

本轮实际运行并通过：
`go test ./internal/app -run '^TestUnixStartup_(SourceAuthorityCannotActivateDaemon|MarkedServiceRequiresActivation|PendingAndUnknownNeverBootstrap)$' -count=1 -v`。
这些测试确认的是**目前严格拒绝 source 的行为**，不是补充功能已修复。

待写入设计并审核的方向（尚未定稿/实现）：

- 保留普通前台、其他平台和任意 pending 的拒绝规则；只有 macOS 新合同服务进入专门的授权读取/选择流程，不能直接放宽通用 CheckDaemonInstallJournal。
- 将现有 RestoreStart intent/done 明确为受 installer 约束的恢复检查点：所有资源恢复完成或已证明未变、持久检查点先于释放 gate、之后不得追加数据/binary/definition 内容恢复。处理重放和检查点之后再次 Stop/恢复使旧依据失效的情况。
- source+complete 是已恢复服务的持续启动依据，不要求存在 RestoreStart，也不要求旧 Running=true；覆盖 stopped/Enabled=true 的跨 boot 启动。
- 授权必须绑定可信 OldDefinition、对应旧 binary hash 与旧布局；不能用升级目标 CandidateHash 授权旧 binary。非 binary 变更 lifecycle 的 hash 来源需要单独严格限定。
- 两次检查保留真实 phase，重新核验同一对象的授权连续性；不能伪装成 complete、空 phase 或 validation mode 绕过下游检查。
- 可考虑把已完成核验且登记成功的只读内存授权结果沿现有 options 传到 daemon/runtime/Manager，统一消费；不增加持久字段或授权文件。类型、生成点、依赖方向和所有消费点仍需在设计中定稿，不能把一个随意可设的 bypass bool 当实现。
- 增加贯穿真实生产 startup reader、装配、runtime/Manager 的恢复测试；fake 只替换进程/IO 边界。正向必须覆盖 pending source、intent→done→complete、完成后重启、旧 stopped/enabled、禁启策略收口；负向覆盖未完成资源、错 hash/layout、旧检查点、无标记、validation 和普通 pending。
- 在 hosted Darwin 上最终验证实际 daemon Ready 与业务可用；看到 launchd job/PID 或 fake running 不足以验收。
