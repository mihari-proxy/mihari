# Issue #331：YAML 导入开发准备

- Issue：https://github.com/mihari-proxy/mihari/issues/331
- 开发分支：`feat/331-yaml-import`
- 基线：`origin/dev`，`49918e6`
- 状态：开发环境已建立；本文记录范围与实施顺序，不代表接口设计已定稿。

## 已确认的核心语义

采用 Import from YAML：读取用户选择的 YAML，保存独立的原始内容缓存，再结合 Mihari 当前设置生成交给 mihomo 的运行配置。

TUI 管理会覆盖运行模式、日志级别、已托管的 TUN 开关等参数；端口、controller 地址与 secret 由 Mihari 管理。调整作用于生成配置，不修改原始 YAML 或导入缓存。

运行和切换使用最后有效主 YAML 缓存。条目记录源文件路径，手动更新和定时刷新都从该路径重新读取、校验并更新缓存。主 YAML 源文件删除、移动或不可读取时刷新失败，但不应使最后有效主 YAML 缓存失效。该保证不覆盖 YAML 引用的外部文件：引用文件直接由 mihomo 使用，变化和不可用可能影响运行或后续启动。

## 首版工作范围

1. CLI/TUI 添加 YAML 导入入口，并在现有订阅管理中展示和切换。
2. daemon 负责导入校验、缓存提交、运行配置生成与应用；客户端不写业务文件。
3. 记录文件路径，提供手动刷新，并与远程来源一样支持定时刷新及关闭自动刷新。
4. 复用候选配置校验、revision/对象版本复查、原子发布和 reload 失败回滚。
5. Mihari 不为主 YAML 引入 watcher；后台按条目刷新设置定时重读，不要求 CLI/TUI 保持运行。mihomo 原生支持监听的文件引用保留其监听行为。
6. 允许本地文件引用，由 mihomo 原生处理；Mihari 不复制引用文件，不增加多文件缓存事务。URL 引用继续交给 mihomo 下载和管理。
7. 创建新 sub 时校验后提示外部文件依赖后果，用户同意才继续。本地来源与远程来源均适用；后续编辑、刷新和启动不重复确认。
8. 订阅页添加表单和首次设置向导都提供明确的 toggle 切换 URL 与本地文件模式，默认 URL；布局、字段、按钮、焦点和状态反馈沿用现有添加订阅页面风格。切换时清空 URL/文件路径来源输入，不保留各模式来源草稿；名称与刷新设置等共用字段不因来源切换清空。已有条目类型固定，不允许跨类型切换。

## 实现前需要定稿的合同

- 来源复用现有 url 字段，本地路径规范化为 file URI，通过 scheme 区分类型；不新增冗余 source_type/file_path。旧版本不支持本地条目，降级前需移除本地条目或恢复兼容备份。
- CLI 使用 --file PATH，内部规范化为 file URI；已有远程 URL 入口保持。
- 绝对路径及 file URI 的平台语义，包括 Windows 盘符、UNC、转义和符号链接。
- 系统 daemon 的文件访问授权，尤其是 Unix 全本机用户控制接口与 root 文件读取能力之间的边界。
- 本地来源首次读取和校验成功才创建条目；失败不留下条目。刷新失败保留已存在条目和有效缓存。具体提交事务仍需设计。
- 本地来源与远程来源禁止互相转换。是否允许修改同类型来源路径及其生效时机待讨论。
- 区分本地输入文件引用与 HTTP provider 的缓存路径；HTTP provider 的 path 不应触发外部输入文件风险确认。需要按 mihomo 字段语义识别，不按字段名 path 一概提示。
- 创建前校验、确认与提交如何绑定同一候选需要定稿。非交互 CLI 使用 --allow-file-references 明确同意；检测到文件引用但未提供 flag 时，反馈说明并明确提示提供该 flag。

公开契约、持久化格式和安全边界的具体变更需先展示影响并按仓库规则确认，不能把本准备文档当作对未定方案的批准。

## 设计访谈：第一轮反馈

- Q1：确定由 daemon 按自身操作系统权限读取用户指定的普通文件；不新增允许目录或调用者权限模拟。用户已确认系统 daemon 可使用高权限读取这一边界。读取失败须提供清晰的 TUI 错误反馈。
- Q2：确定保存文件路径，作用等同于远程来源记录 URL；从源路径重新导入即更新行为。
- Q3：确定本地首次导入校验成功才创建，失败不留空条目。
- Q4：确定禁止本地与远程来源类型转换。
- Q5：确定不做 watcher，但支持与远程来源相同的定时刷新和关闭自动刷新。
- Q6：确定修改来源路径时保留旧缓存和运行配置，标记来源与缓存不一致；后续手动或定时刷新成功才替换内容，路径编辑本身不 reload。
- Q7：确定允许符号链接，每次刷新读取当前链接目标；实际打开目标必须是普通文件，悬空链接及非普通文件返回明确失败。
- Q8（最新决定，替代拒绝方案）：允许文件引用并交给 mihomo 处理，不复制引用文件；本地和远程新 sub 均在校验后说明后果，用户同意才创建。仅创建时确认，后续操作不重复确认。URL 引用继续由 mihomo 管理。
- Q9：接受 --allow-file-references 作为 CLI 明确同意方式；非交互模式检测到文件引用但缺少 flag 时，须明确提醒用户提供该 flag。交互 CLI/TUI 使用默认取消的确认，无文件引用无需确认。
- Q10：本地和远程新 sub 统一为取得内容、校验、必要的文件引用确认、创建提交；获取或校验失败不留下条目。该决定替代远程 add 原有先注册再首次获取的失败保留语义。
- Q11：确定本地主 YAML 的相对文件引用按源 YAML 所在目录解析，生成运行配置时改为绝对路径；原始 YAML、主缓存及引用文件不修改。远程订阅保持 mihomo 原生工作目录语义。
- Q12：确定主 YAML 为符号链接时，以本次读取的实际目标所在目录作为相对引用基准；后续刷新链接切换目标时重新解析。
- Q13：确定 CLI 增加 `mihari sub add NAME --file PATH` 与 `mihari sub set ID --file PATH`。URL 与文件参数互斥，保留现有远程入口；创建存在文件引用时使用 --allow-file-references 明确同意，不允许通过 set 转换来源类型。
- Q14：确定主 YAML 和引用文件均允许任意路径，不维护允许目录列表。为满足引用文件目标，需要配置核心避免拒绝工作目录之外的路径；用户已明确接受该执行安全边界调整。操作系统权限仍适用，读取/校验失败仍明确反馈。具体核心环境实现及跨版本能力验证待技术设计。
- Q15.1：采用 A，复用现有 url 字段记录来源，本地保存规范的 file URI；类型由 scheme 区分，不另存来源类型和文件路径。
- Q15.2：接受缓存记录该次成功读取主 YAML 的实际目录，随缓存一起提交/回滚；使用旧缓存时不根据当前来源或链接目标重新解释相对引用。远程条目省略本地目录元数据。字段命名待技术设计。
- UI 新要求：来源配置页面明确提供 URL/本地文件模式 toggle，符合现有添加订阅页面设计风格。不能因为增加 toggle 而撤销禁止已有条目跨来源类型转换的决定。
- Q16：接受订阅页添加表单与首次设置向导同步提供 toggle，交互一致。
- Q17：不保留模式来源输入。切换时清空 URL 和文件路径，不恢复上一模式来源草稿；按问题范围理解，不清空名称、刷新间隔等共用字段。默认 URL 模式。

当前事实：Unix 系统控制权限为全本机用户共享；现有服务端没有请求者 UID 授权。daemon 按自身权限读取，不声称源文件必须对请求用户可读，也不把客户端验证 daemon owner 的 peer UID 校验误认为请求者文件访问授权。

### 已确认的读取失败处理

- 文件不存在、访问被拒绝、不是普通文件、读取失败或 YAML 校验失败，应保留实际原始原因，经过既有错误分类与诊断快照反馈到 TUI。
- 手动操作立即显示失败概要，F2 可查看具体路径及原始原因；终端显示转义控制字符。
- 定时刷新失败保留条目的失败状态并记录诊断，使 TUI 后续加载或重新连接也能看到失败；不要求用户正在运行 TUI。
- 首次导入失败不创建条目；已存在条目刷新失败保留最后有效缓存与运行配置。
- 一次失败由执行 owner 记录一次，不因 TUI 读取状态或查看诊断重复记录。

### 文件引用创建确认

- 不再采用“暂不支持文件yaml引用”的拒绝提示。存在文件引用时，在新 sub 校验成功后、创建提交前说明后果并取得用户同意。
- 告知用户：Mihari 只缓存主 YAML，不备份引用文件；mihomo 原生支持监听的引用文件可能随修改直接影响运行，不受主 YAML 的定时刷新开关控制；文件移动、删除或权限变化可能影响运行、校验或重启；主 YAML 回滚不代表引用文件内容一起回滚。Mihari 不修改引用文件，但不能承诺 mihomo 所有文件引用处理都只读，原生 bundle fallback/SideUpdate 等路径可能写入。
- 本地 YAML 导入和远程订阅创建均适用。后续编辑、手动/定时刷新、切换和启动不重复询问。
- 提示列出识别到的引用位置与实际路径；不为提示读取或转储无关文件内容。
- 用户拒绝则不创建条目。操作失败仍通过原有诊断机制反馈，并保留最后有效主 YAML 缓存和运行配置。
- HTTP provider 的 path 是其原生缓存位置，不等同于本地输入文件引用；URL 引用沿用当前 mihomo 下载、刷新与缓存职责。
- 本地引用按主 YAML 本次读取的实际目标所在目录解析，绝对路径保持指向原文件；远程来源保持原生工作目录语义。符号链接在每次刷新时重新解析，主 YAML 缓存需要关联该次解析基准，以免离线生成按当前链接目标错误重解释旧内容。
- 已决定允许所有引用路径，核心执行需落实该语义；完整识别字段范围仍需明确，不宣称每种文件依赖都有 watcher。

### 核心安全路径核验事实

- mihomo file proxy/rule provider 的绝对路径仍要求位于 -d HomeDir 或 SAFE_PATHS；daemon 可读取主文件不代表核心允许其引用路径。
- 当前 Unix root 可信核心以 D/runtime/core-home 为 HomeDir，固定环境不传 SAFE_PATHS；普通执行以 paths.Root 为 HomeDir，并继承环境。项目没有现成的按 YAML 来源目录维护 SAFE_PATHS 的机制。
- SAFE_PATHS 在核心启动时取得，仅改生成 YAML 不能给正在运行的核心增加允许目录；如设计新增授权目录，需明确安全边界和重启语义。
- 旧 catalog 严格解码，实际包含新增来源/目录字段的目录不能由旧版本读取；省略新增字段的远程记录可保持既有格式。最终字段及降级说明待用户确认。
