# 核心版本修正：完成情况与范围复审

日期：2026-09-19。状态：Q1–Q3 及整体范围已获用户“通过”，按收敛清单恢复实现；保留现有未提交改动供取舍。本记录修订 [2026-09-17 设计](../specs/2026-09-17-core-version-and-update-design.md)及其[执行计划](2026-09-17-core-version-and-update-plan.md)，不能将旧计划的技术机制继续视为本次全部必做项。

## 已确认的范围修订

**Q1=A，用户已确认：常规失败自动回滚；强杀／断电后人工恢复。**

- daemon 正常运行期间，下载、摘要与配置校验、替换、设置保存、新核心启动及初始健康验收失败，保留或恢复旧核心、原通道和原运行意图。
- 回滚也失败，保留恢复材料与两次失败原因，停止自动尝试。
- daemon 被强杀或机器断电后，保留备份、检测未完成更新并阻止不确定的核心启动；不自动完成或恢复整笔事务。
- 因此仍需要最小的持久中断／阻断证据。不能用进程内 bool 代替重启后的检查，也不能删除恢复所依赖的旧格式兼容。
- 完整的跨崩溃阶段重放、自动恢复后重试、据此扩展的全阶段恢复机制不再是本次交付要求。已有相关实现的具体去留待访谈收口后处理，不据此直接删除文件。

**Q2=A，用户已确认：统一产品行为，保留现有保护并补必要检查。**

- 三平台统一官方版本选择、本地已有核心接纳和更新失败结果。
- 保留各平台现有保护，补齐本次下载、候选替换和回滚所需的权限及文件身份检查；不降低 Unix root 现有保护。
- Windows／非 root Unix 的完整持续执行前检查体系移出本次，不以统一产品行为为由强制套用 Unix root 的全部执行模型。
- 当前 `VerifiedCore` 中解除 receipt 准入耦合、保留原有对象身份保护的改动仍服务于 Unix root 解锁；其是否保留不能与新增三平台执行体系混为一谈。

**Q3 已确认：用户一键重新安装 mihomo，使用更新前原通道的官方最新版。**

- 这使“人工恢复”可以表现为用户主动触发重新安装，不再仅限手工操作文件；不据此恢复完整跨崩溃事务重放的范围。
- 仅重装 mihomo，保留订阅、配置和 Mihari 安装；按更新前已确认的通道重新解析官方最新版，并在本次重装期间固定目标。例如 stable 切换 alpha 失败后，重装 stable 最新版。
- 原通道无法可靠确定时不得静默改成 stable 或猜测失败操作目标；保持阻断并报告缺失信息，由用户明确选择通道后再发起安装。这是异常材料不足时的处理，不新增自动通道推断机制。
- 核心缺失、损坏或更新中断可进入修复；配置错误、网络失败、权限不足等仍报告具体原因，不能承诺重装可修复所有错误。
- 重装失败继续保留旧备份、诊断和阻断；通过候选检查、设置提交及适用的启动验收后，才解除阻断。无需恢复尚未确认可靠的旧核心来探测版本。
- 现有 degraded daemon 保留诊断，但未装配业务 Runtime；不能将增加按钮视为已能调用正常安装路径。需核实并设计最小的 daemon 修复执行路径，保持单写入者。
- 只读核查：`internal/control/server/runtime.go` 的 `/v1/core/install` 先要求 Runtime；TUI System 的核心更新行要求核心能力及可写状态，因此降级模式不能直接复用按钮完成修复。正常 Manager 的 `coreRecovery` 也会阻止新的安装；修复路径必须受控处理旧中断记录及备份，不能先删除标记绕过阻断。TUI 已有“服务重装”仅重注册系统服务，不是 mihomo 核心重装。
- 原通道最新版重装是新的主动操作，不要求重新取得失败操作当时的资产；解析后仍固定此次目标。它不重放旧事务，不赋予普通“重启核心”命令修复语义，也不因每次启动自动下载安装。
- 此决定仅确定产品与范围边界，不表示修复入口已经实现。

## 不重新推翻的产品需求

官方 stable/alpha 在线最新版；离线包可使用内附官方核心；Mihari 更新保留已有核心与通道；本地已有核心不强制官方 provenance；有上游摘要必须验证、缺摘要警告继续；固定本次更新目标；三平台结果一致；保留现有权限、单写入者和本地协议边界。六个 OS/arch 构建目标是仓库既有支持范围，并非本次新增产品能力。

## 范围扩张的具体位置

原有 Unix `replaceBinary` 仅完成 rename，Windows 的替换备份在替换成功后即删除；旧 `commitTrusted` 的 pair WAL 保护 binary/receipt 文件对，并在 Manager 保存通道和重启前完成清理。原有 `Maintain` 不提供同一回调内试启动、健康确认和失败恢复。因此，延长备份生命周期、协调停止／试启动／恢复、补偿核心设置，是兑现已确认回滚行为的必要修改；不能将所有 Supervisor 改动一概认定为越界。

范围扩张在于把上述单次更新保证进一步升级为：新 `mihari.core-update/v1` 全阶段持久事务、跨 daemon 重启或断电自动恢复、恢复入口语义扩展，以及尚待明确的跨平台完整执行能力改造。旧 pair WAL 本来就存在，不应计为此次新增；其文件身份与原子操作可复用，但不能原样承担新增通道和健康语义。

还有一项可复用机制需要纠正先前判断：`cmd/mihari/main.go` 的 `runDaemonWith` 已在 runtime 构建失败时转入 `runDegradedDaemon`，保留不带业务运行时的本地控制面与诊断，已有 `TestDaemonAssembly_RuntimeBuildFailureIsRecordedBeforeDegradedStartup`。不能仅因 `BuildRuntimeWithOptions` 返回错误，就认定必须重新建设整套 degraded daemon。Unix 更早的权限／旧 WAL 准备错误仍可能直接返回；需要核对具体错误发生在哪个阶段，不能把通用降级能力等同于所有中断场景已经覆盖。

## 收敛后的验收边界

1. 三平台官方 stable/alpha 在线安装、更新与版本检查规则一致；已有本地核心及离线包不受编译版本表卡死。更新 Mihari 不强制更新核心。
2. 下载准备期间旧核心继续运行；普通校验、发布、设置或启动失败，恢复旧核心、原通道与运行意图，明确返回失败。回滚失败保留材料并阻断。
3. 中断后重新启动能检测未完成更新、显示诊断并阻断不确定核心；不自动重放事务或重试安装。
4. 用户主动重装按更新前原通道解析官方最新版，版本相同也能重新取得并替换损坏核心；订阅与非核心配置保持。失败保留备份及阻断，成功验收后解除阻断；原本停止则不擅自启动。
5. 用 fake 核心／合成下载覆盖普通回滚、中断检测、降级重装、重装失败与再次中断，验证不会绕过权限或留下无人管理的子进程；不扩展为所有阶段的自动恢复重放测试框架。
6. 最小行为测试通过后完成相关集成、全仓检查、六目标无 CGO 编译，以及 PR 的 CI/bot review；平台和环境未验证项明确说明，不以当前三个包测试通过代表交付完成。
