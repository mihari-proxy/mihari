“完整”指在已有日志出口、日志级别和明确资源上限内，记录可获得的真实原因，不用类型名或固定摘要替代已获得的诊断信息。它不承诺在进程被强制终止、磁盘不可写、日志已轮转淘汰或上游已经丢失内容时恢复原文。

“取消脱敏”适用于持久化日志及日志快照、导出内容，不扩大普通状态接口、错误 envelope、CLI JSON 或浏览器业务响应的内容范围。它允许保留错误自带的配置片段，不要求每次失败额外读取和转储完整配置、成功响应或凭据文件。

## 4. 原因保留、记录责任与级别

### 4.1 原因和用户输出

- 底层返回实际错误；需要公开分类时，保留内部 cause，不以新建简短 `APIError` 替换掉原始原因。
- 日志包含原始错误文本、包装上下文、合并分支及可获得的系统/HTTP/进程详情。不得只输出 `error (*errors.errorString)` 或固定的解析/命令失败摘要。
- 普通 `Error()` 与公开 DTO 不隐式展开内部诊断。诊断输出仍由日志边界显式执行。
- 原文中的换行、引号和控制字符按 JSON 格式转义；合法 UTF-8 内容不得因展示整洁被合并或删除。非法 UTF-8 保留替换和可识别标记，不能输出无效 JSON。
- 不伪造错误发生时的堆栈。已有堆栈和已捕获 panic 的堆栈在日志可用且限额内保留；保留既有 panic 传播/退出语义。

### 4.2 错误事件

| 事件 | 默认级别 |
| --- | --- |
| 预期参数拒绝、revision/所有权冲突、用户主动取消 | INFO |
| 可重试的失败尝试、可恢复降级、提交后同步 warning | WARN |
| 未恢复的操作失败、补偿失败、后台任务异常退出 | ERROR |
| 不表示错误的请求阶段、缓存重放、常规调试细节 | DEBUG |

默认 INFO 可以看到全部上述错误事件；用户把日志级别提高到 WARN/ERROR 时仍按配置过滤，不绕过已有级别选择。

正常协议 EOF、循环终止哨兵等不能仅因使用 `error` 类型就被虚构为失败。由 owner 判断其业务语义；实际参数拒绝、取消和失败则不得以“预期内”为由直接静默。

重试中不同尝试的失败是不同事件，需要保留各次原因及尝试顺序；最后一次失败由最终 owner 记录，不再先记同一原因的重试 WARN。恢复成功时给出可关联的恢复结果。日志不能改变现有重试策略、次数或超时。

主操作、回滚和清理失败保留各自原因，不能让后一个错误覆盖前一个。最终聚合记录可包含多个原因，但不能据此逐层重复记同一故障。缓存命中或等待同一执行的调用者继续复用已记录标记。

已提交 settings 的同步 warning 保持成功、revision 与内存发布；日志不能触发回滚或改成失败响应。

### 4.3 跨模块记录责任

模块范围按实际错误流闭环验收。底层保留 cause，执行 owner 记录结果，表现层生成用户提示；日志 formatter 无法恢复底层已经丢弃的内容。

| 实际路径 | 原因产生与传递 | 最终记录责任 | 用户输出责任 |
| --- | --- | --- | --- |
| CLI/TUI 发起 daemon mutation | `control/client → control/server → runtime → subscription/core/panel 等业务包 → platform/外部适配器`；cause 随内部错误返回 | 实际执行的 runtime 或业务 owner；server 仅兜底未记录失败，重放和等待者不重复 | server 生成既有安全 envelope；client/CLI/TUI 使用公开错误 |
| 后台刷新或核心健康检查 | `app/supervisor → scheduler/业务包 → 网络或进程适配器` | 自主任务 owner；分别记录失败尝试、最终失败或恢复 | 状态与事件仅发布原有公开信息 |
| 客户端本地 IPC、读取或解码失败 | `control/client → credential/transport/protocol` | 有既有 reporter 时由客户端本地 owner 记录；远端已返回的业务错误不再作为本地故障重复报告 | CLI/TUI 保持原有错误码、退出码和展示 |
| 本地安装、自更新或系统服务任务 | `cli/tui → app → service/update/platform` | 当前任务已有可用 reporter 才记录；普通 CLI 与 TUI cleanup 后路径的无出口边界按 Q2 接受 | 本地 renderer 保留既有失败及部分成功语义 |
| 日志导出 | `tui → control/client/server → logging snapshot/assemble/export` | 导出任务 owner 记录最终结果；底层采集失败保留原因，独立资源故障走 FailureReporter | 共享导出页面显示结果及红色未脱敏说明 |

每条链路都需同时验证“文件中的原始原因”和“用户可见结果”，不能只检查其中一端。协议包保留原因的实现不得反向依赖 `diagnostics` 而形成依赖环；公开 DTO 继续只承载稳定字段。

## 5. 文件出口和生命周期

- “有日志文件”以当前执行路径已取得可用的文件 logger/reporter 为准，不是 `Stat` 某个历史路径。
- daemon/TUI 沿用现有创建和关闭日志资源的生命周期、固定来源、目录、权限、跨进程锁与轮转配置。
- 普通 CLI 不新增文件、不查找历史文件、不借用 daemon/TUI 日志。CLI 请求实际进入 daemon 后，由 daemon 对自身执行负责。
- 没有 reporter、启动日志尚未建立、TUI 日志已经关闭的路径，接受没有持久化记录；不能为了补日志延长已结束的资源生命周期。
- logger 自身故障仍交给现有独立 FailureReporter 出口；禁止递归写入失败 logger，不增加无限队列、无限重试或无 owner goroutine。此类终端兜底属于独立输出策略，不自动套用文件日志原文策略。
- 日志可用时尽量在返回精简错误/发布用户状态前报告实际结果；报告在业务锁外执行，不把日志成功作为业务提交成功的条件。

## 6. 长度、编码与日志流兼容

诊断文本、保留的 HTTP 错误正文、mihomo 单个逻辑输出行的内容预算各为 **256 KiB = 262144 字节**。文字按 UTF-8 字节计数，超出时保留合法字符边界并明确标记截断；总诊断文本预算不会因 HTTP 正文加上其他原因而无限增加。

保留循环检测和错误图深度/节点边界。达到任一边界都必须可识别，不能输出一个貌似完整的片段。超限读取仍需取消、超时和资源关闭，不为取得被截断尾部无限读取网络或进程输出。

上游库在返回前已经缩短的内容无法靠提高日志限额恢复，例如现有 WebSocket 握手响应副本。实施中核查各入口的真实可获得长度，并对仍受上游限制的场景保留准确标记，不宣称一律取得 256 KiB 原文。

**256 KiB 是逻辑内容预算，不是 JSONL 物理记录或 IPC frame 大小。** 现有导出和 `/v1` 机器日志快照的单记录上限为 1 MiB，frame 上限为 2 MiB。JSON 转义可能使 256 KiB 原文超过 1 MiB，不能仅提高 formatter 常量后把新日志交给旧 reader 丢弃。

设计采用：保留既有快照协议大小契约；需要时在写日志阶段把一个有界逻辑诊断分成多个完整 JSONL 记录，携带可区分并发逻辑记录的标识、片段顺序和结束/截断信息。每条编码后的记录（含元数据和 LF）须满足既有读取预算；每个独立诊断值（包括其完整 cause 图）仍受 256 KiB 限制。同一记录包含多个独立 error 属性时，分别保留各自预算，避免后一个原因被前一个挤掉。分片不产生新的业务 operation ID，不增加公开错误 DTO，不把片段数量计作多个实际故障。

具体规则：正常编码后适合预算的记录保持单条；仅对超过物理预算的诊断或核心输出，把原始正文按 UTF-8 边界切成至多 64 KiB 的片段。诊断字段也包括调用方使用任意键名传入的 error 属性，不能只识别 `cause`；已受 256 KiB 约束的文本属性可作为分片正文，时间、级别、组件、事件和操作身份等保留元数据不切分。每条都保留原始 time、level、component、event/stream、既有 operation metadata，并增加日志内部字段 `record_id`、`fragment_index`（从 1 开始）、`fragment_count` 和 `truncated`。`record_id` 与业务 operation ID 分离，只关联一次逻辑记录，不能取“当前请求”的全局状态。标识生成使用可注入的有界本地来源；生成失败通过既有独立日志故障出口报告，不阻止业务、不生成可能混淆的固定 ID。

物理预算按编码结果检查，不能只用字符数估算。先限制完整逻辑正文，再分片；多字节边界可使片段数略多于四条，必须按实际切分结果填写总数。多个大字段分别切分，每片仅填充其中一个大字段，其他大字段为空串；按片段序号逐字段拼接可恢复原文。一次最多处理 64 个大字段，编码输入与待写片段总量均限于 `64 × 6 × 256 KiB + 1 MiB`，避免验证阶段无界分配。若外围属性、字段数或编码总量超限，明确通过独立 FailureReporter 报告日志编码/容量故障，不能静默丢字段后声称原文完整。各片段以完整 JSONL 记录通过现有受锁 writer 写入；允许不同操作的片段交错，靠记录标识和顺序区分，不扩大业务锁或承诺跨多片段的磁盘原子提交。

这项配套处理须覆盖 handler、core capture、轮转、daemon snapshot、control client 和最终导出；不能只在本地 exporter 放宽上限，导致 Unix 系统模式仍无法导出。分片跨轮转或选定时间窗口不完整时不能伪装成完整诊断。

## 7. 取消日志脱敏与导出提示

取消日志内容处理链上的秘密替换、URL 整体隐藏、路径隐藏、属性删除及保守类型摘要，包括：

1. 领域/HTTP 适配器在封装诊断前的替换。
2. formatter 和 JSON handler 的消息、属性、已绑定属性处理。
3. daemon machine snapshot、TUI 本地日志源装配。
4. control client 的二次脱敏。
5. 本地 exporter、组装 exporter 和导出说明。

不能整体删除同时服务公开错误提示的辅助逻辑。公开 `APIError`、状态、事件、CLI JSON、浏览器普通业务响应仍按原职责输出；唯一允许携带日志原文的协议路径是已有授权和范围约束下的日志快照。

保留快照与导出既有 `redacted` 字段；新路径没有实施内容替换时为 false/0，不改 schema，不把历史文件中的 `***` 误计作本次脱敏。新客户端对旧 daemon 的统计继续如实保留；旧日志已丢失的内容不可能恢复，旧客户端仍可能按旧策略处理新日志。

共享导出 overlay 位于 `internal/tui/ui/exportlogs.go`，由 Logs/System 页共同进入。进入导出页即可看见以下红色说明，导出完成后也保持可见；不新增确认弹窗或必须勾选项：

> 日志未经脱敏，可能包含密码、访问令牌、完整订阅地址及用户配置。分享前请自行检查。

实际文案遵循现有界面语言；使用既有危险提示颜色，并保留明确文字供无颜色终端阅读。ZIP manifest 的说明同步表达未脱敏，不再暗示凭据已经移除。不把配置、token 等独立文件额外加入 ZIP。

## 9. 验收要求

- 以原始 fixture 错误为依据断言日志保留文本、包装上下文、多个原因、路径、URL、凭据和配置片段；同时断言用户 envelope/状态没有混入内部 cause。
- 文件、网络、HTTP 状态/正文、配置解析、子进程退出、回滚/清理、后台任务、参数拒绝、取消和重试恢复均有代表性故障注入；新修复先运行失败回归，再运行实现后的相关测试。
- 各包模块登记明确实际覆盖入口和测试。不能用 formatter 单测代替业务链路审计，不能用一条成功日志证明所有失败可见。
- 同一故障在 owner/控制兜底/客户端之间不重复；并发请求、缓存重放和多次尝试的记录身份不混淆。
- 无 reporter 时正常返回原有结果，不新增目录、文件或打开历史日志；已关闭 logger 不再被使用。
- 256 KiB 前后边界、中文/多字节字符、JSON 最坏转义、已有堆栈、合并/循环错误、核心半行输出均有测试；截断与分片可识别且资源有界。
- 新日志经 daemon/TUI 本地文件、快照 IPC、control client、ZIP 导出后保留相同内容；验证长记录、片段跨轮转、时间过滤和部分来源结果，不能静默因 reader 大小限制丢失新记录。
- 记录数、字节数、摘要、redacted 统计与实际处理一致；旧日志和旧对端边界如实记录。
- 导出前和成功态都有可见红色说明；失败、窄终端和无颜色展示不遮挡主要操作或遗漏文字。
- logger 写入/关闭失败继续采用现有有界兜底；不能把业务成功改为失败，不能递归或造成死锁。
- 运行受影响包、相关集成测试，再按范围执行 `go test ./...`、race、vet 和 gofmt；当前平台之外的原生测试未运行时明确标记。
- 保持 `CGO_ENABLED=0`，验证 Windows/Linux/macOS 的 amd64/arm64 构建；构建不等价于对应平台原生行为已测试。
- 不使用真实订阅、真实用户配置、真实 mihomo 或系统服务安装做默认测试；不修改 CHANGELOG，不覆盖用户已有修改。
