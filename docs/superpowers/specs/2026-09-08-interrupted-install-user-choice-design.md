# 三平台安装中断提示与重新安装策略

**后续确认（2026-09-08）：** 用户已批准具体实现设计，并要求保留产品全英文特性。下文中文说明表示语义，所有实际界面、按钮、帮助、错误和确认输入均使用英文；本要求覆盖此前中文文案示例。实施进度见实施计划，不以设计批准代替功能验收。

日期：2026-09-08。修订：R5 策略稿。Windows、Linux、macOS 统一采用用户已选定的简单流程：检测到安装事务中断后提示用户，由用户选择修复安装或全新安装，不自动恢复中断事务。本稿记录已确认的交互和恢复边界；具体契约见已批准的 [实现设计](2026-09-08-install-repair-implementation-design.md) 和 [实施计划](../plans/2026-09-08-install-repair-implementation-plan.md)。用户随后授权实施、提交和推送当前成果；功能仍在开发中，真实工作站系统服务验证不在该授权范围内。

**用户已确认的五项边界：** 安装完整与启动失败分开；准确识别中断而非连接/权限故障；修复入口独立于旧程序；明确保留数据且不自动改为清除；修复再次中断仍提示用户选择。以下作为后续实现的固定要求，不再作为待选方案。

本稿取代 [macOS 补充设计 R4](2026-09-08-darwin-runtime-group-handoff-addendum.md) 中“自动恢复中断事务、恢复 action 重放、为自动回滚增加 pending source 启动授权”的工作方向。R4 留作历史，不作为这些功能的实施依据。不修改冻结的 Unix 基础架构文档；实现前必须同步受本决策影响的实际行为文档和计划。

## 1. 适用范围

这里的事务指安装、升级、安装数据迁移、服务重新注册或卸载等安装管理操作，不指代理连接、流量、普通配置提交或 daemon 的内存状态。

- 正常运行期间断电，没有未完成安装事务：从完整、可信的已安装状态正常启动 daemon/mihomo。
- 安装操作仍有有效执行者：显示“安装正在进行”，不弹中断提示、不接管、不启动第二个安装器。
- 发现可信的未完成安装记录，且对应操作已经结束：提示中断，等待用户选择。
- 记录损坏、权限不足或仅连接失败：分别提示“安装状态无法确认”“需要权限检查”或连接问题，不能凭这些现象断言事务中断。
- 已有服务正常停止、用户主动禁用服务、尚未安装，都不等于安装中断。
- 程序及服务定义已完整、所需安装资源已验证并持久提交，但服务因端口冲突、配置错误或启动超时不可用：归类为“安装完成，服务启动失败”，显示具体原因和重试启动入口，不弹事务中断/重装建议。

应用启动、状态查询、打开 System 页面，以及普通 start/restart/update，不得隐式调用恢复来补做中断事务。检测本身只读，不删除日志、不改 phase、不回放旧 action、不替用户选择安装方式。当前运行进程内的单文件原子替换失败处理、临时资源关闭和普通配置失败回滚不因此取消；它们不属于接管另一次中断安装。

### 1.1 安装状态与运行状态分别判断

安装是否完整以可信的安装资源校验和持久提交为依据；服务是否可用以实际进程及控制面 Ready 为依据。安装执行者退出不等于安装失败，服务 PID 存在也不等于安装完成。

| 可验证事实 | 向用户呈现 | 后续行为 |
| --- | --- | --- |
| 有效安装执行者仍持有操作权限 | 安装正在进行 | 等待，不接管。 |
| 可信未完成记录，且对应安装执行者已退出 | 检测到事务中断，建议重新安装 | 显示两个安装选项，允许稍后处理。 |
| 安装完整且服务按预期运行 | 已安装、运行中 | 正常使用。 |
| 安装完整且按用户策略保持停止/禁用 | 已安装、已停止/已禁用 | 保留策略，不要求修复。 |
| 安装完整、要求启动但未 Ready | 安装完成，服务启动失败 | 显示原因，允许修正问题后重试启动。 |
| 证据缺失/损坏、权限不足或仅连接失败 | 状态无法确认、需要权限或连接失败 | 提示对应问题，不推断事务中断，不自动写入。 |

识别执行者不能只查 PID；须通过平台所有权/进程身份与互斥证据核对同一次操作，避免 PID 复用或检查期间的新安装被误判。检测结果和之后执行用户选择之间必须重新验证。数据不明时不因用户点重试就跳过安装完整性检查。

## 2. 用户交互

TUI 检测到确认的中断时显示：

> **Installation needs attention**
>
> An interrupted installation was detected. Reinstallation is recommended.
>
> Repair keeps your configuration, subscriptions, settings, and logs. A fresh installation resets only the managed data shown in its preview.

按钮：

1. **Repair installation (keep data, recommended)**
2. **Fresh installation (reset managed data)**

允许关闭弹窗或选择“稍后处理”。默认推荐修复安装，但预选不等于执行。全新安装必须另行展示准确数据路径和删除项目，二次确认后才执行；不能通过普通“安装/升级”确认代替删除确认。

同一实例、同一中断状态在一次 TUI 会话内只主动提示一次。关闭后在 System 页面保留修复入口，不在每次刷新时重复弹窗。后台检测结果只通知 UI，不直接触发安装。

“安装完成，服务启动失败”使用独立提示，提供具体错误摘要、**重试启动**及关闭操作，不默认引导重装。错误若需要先修改配置或释放端口，明确说明；不自动修改配置或终止占用端口的其他程序。

| 入口 | 表现 |
| --- | --- |
| Windows/Linux/macOS TUI | 使用相同文案和两个选择，复用终端模态交互。 |
| CLI | 输出中断及保留/清除数据的区别，指向显式安装入口；普通命令不自行进入交互或执行修复。 |
| JSON/非交互/脚本 | 沿用既有错误 envelope/退出码分类返回失败和可理解原因，不弹窗、不等待输入、不默认删除或修复。新的命令选项/结构化字段须在具体 CLI 设计中单独列明，不能悄悄修改契约。 |
| OS 后台服务 | 不从 SCM/systemd/launchd 中启动桌面弹窗或提权 UI；记录可诊断错误，由用户下次打开 TUI/CLI 时展示处理入口。 |
| 程序本身已损坏、不能启动 | 用户重新运行独立安装脚本/安装包也应得到相同保留/清除数据选择；不能依赖已损坏的旧 daemon 来完成修复。 |

## 3. 修复安装的保证

修复安装重新部署受支持的完整程序和服务定义，验证后按用户选定的运行/自启策略启动。它不是“先清空数据再安装”，也不是“先自动回滚旧事务，再运行现有 reinstall”。

独立安装包/脚本必须能够在旧 Mihari executable 缺失或无法执行、daemon 不可连接时检查安装并执行用户选择的修复。可由新下载且已验证的完整程序提供安装能力，不能先调用损坏旧程序的 recover/uninstall 才能继续。仍需获得平台安装权限并验证旧进程退出，独立入口不等于跳过安全检查。

必须保留所选实例的用户业务数据：配置、订阅及其内容、设置/偏好、日志，以及不能确认可重建的用户文件。既有业务目录身份、权限和安全边界仍需验证。不得恢复安装前的数据快照覆盖最新数据，不重新导入旧订阅源覆盖现有数据，不顺带改变数据布局或格式。启动后的正常业务读写按原有语义执行，不承诺修复后所有文件永久逐字不变。

程序与受管理安装资源可重新部署；修改范围必须与业务数据清单分离。token/credential 仍按平台现有身份规则处理，不承诺在服务身份变化时保留旧秘密；不得借重装放宽 ACL 或输出凭据。

若用户数据已损坏、迁移只完成一部分或与所选版本不兼容，保留数据并具体报错。修复安装不保证修好损坏数据，也不得自动降级成全新安装。原始迁移来源、未知文件、其他实例与其他用户的数据均不自动清理。

## 4. 全新安装的保证

全新安装在二次确认后清除所选实例、预览清单内的 Mihari 数据并重新建立默认配置。清单至少明确配置、订阅、设置与日志的删除情况，以及哪些外部/用户文件不会处理。

“所选实例”不代表扫描或删除机器上所有 Mihari 目录。系统服务使用的机器数据与用户 TUI 日志分别显示；其他用户日志、迁移原始来源、目录外路径不纳入默认删除。不得递归删除任意环境变量指向的路径；须经平台能力验证绝对目标、身份与允许范围。

旧进程必须已停止，安装锁、数据锁及业务文件的所有权边界均仍适用。全新安装也不能绕过不明进程、未知 ACL、链接逃逸或损坏的安装依据；无法安全界定删除范围时拒绝执行。中断证据在替代安装安全接管前保留，不能为让检查通过而先删 journal。

## 5. 三平台共同流程与平台差异

共同流程：只读检测 → 用户选择 → 获取安装权限与锁 → 重新核验实例及旧进程 → 生成/验证新安装候选 → 按保留或清除策略部署 → 验证并持久提交安装完整状态 → 按运行策略启动并核验 Ready。检测与确认之间状态改变时重新检查，不能用过期弹窗接管一个新的事务。

安装完整状态必须在对应安装资源及服务定义已验证、同步成功后提交，不能因为 binary 已复制就提前标记完成。首次 Ready 失败不把已完整安装的资源退回“事务中断”，也不自动回滚或重装。若用户要求启动，整体操作不得谎报“全部成功”：结果须明确“安装已完成，服务启动失败”；若用户选择保持停止，则不以缺少 Ready 判失败。具体服务启用策略、提交点与锁释放顺序在实施设计中落实这一划分，不复用一个标志同时表达安装完整和服务可用。

| 平台 | 当前代码事实 | 实现需要处理 |
| --- | --- | --- |
| Linux | `internal/app/installer_unix.go` 等入口先调用 RecoverLocked；使用 Unix journal 与 systemd 定义。 | 将“发现中断”与“恢复副作用”拆开；中断时返回提示，显式重新安装可以安全接管，不能先强制跑旧恢复。按 Linux 进程/服务能力确认停止。 |
| macOS | 共用 Unix 安装事务；本地已有 launchd 共享组代码，登记/gate 补充机制尚未实现。 | 相同选择流程；仍需证明 daemon/mihomo/后代退出。共享组与登记机制不因取消自动恢复就视为已解决，也不复制到其他平台。 |
| Windows | `internal/service/service.go` 的 Reinstall 是停止/注销、安装、启动；PowerShell 安装脚本有独立替换入口。 | 不能宣称已具备 Unix 等价的中断识别。需为 Go 服务安装、自更新和脚本入口建立一致的受保护操作记录与互斥，覆盖执行者丢失、程序替换和服务注册窗口，并使用 Windows 进程/服务能力核验停止。 |

统一的是用户选择、数据保留和验证结果，不要求共用 PGID、launchd 或 systemd 实现。不新增常驻恢复进程，不让后台服务等待用户点弹窗。

## 6. 接管中断安装的边界

- 点击“修复安装”是执行新修复操作的授权，不是批准重放旧事务所有 action。显式“全新安装”额外包含清单内的数据删除授权。
- 即使用户选择重新安装，仍须确认原执行者不再持有事务、旧受管进程已停止，并获得安装/data/endpoint 权限。用户点击不能代替资源一致性证明。
- 旧记录仍用于识别实际实例、可能替换过的程序/定义、需要保护的数据及进程。不能通过删除或覆盖旧记录把未知状态伪装为首次安装。
- 新修复操作应持久接管后再进行副作用；若修复本身再次中断，下次继续提示用户选择，不自动恢复。接管证据必须足以在下一次检测中保留数据范围和安全停机依据，不要求恢复之前每一步的执行进度。
- 保留的最小记录服务于识别实例、操作执行者、数据范围、程序/服务定义的一致性及安装完成状态；不为自动逐步重放扩展恢复日志。重复修复不得丢失最初的数据保留范围，也不能把上一轮未完成的修复当作无数据的首次安装。
- 未完成记录不用于启动未核验的旧 source；不实施 R4 为自动恢复设计的 pending source 内存授权例外。完整可信的已安装状态如何与“安装器进程已退出”区分，必须在后续实现设计中明确，不能仅因缺少进度记录就启动未知组合，也不能仅因安装器退出而停止已经确认完整可用的服务。
- 若无法读写可信记录或无法证明安全接管，保持错误和现场。全新安装不是无条件绕过路径。

本策略不需要承诺自动处理每个断电组合。但仍需保证断电不会使自动启动路径接受未知资源，或使保留数据的修复路径误删业务数据。持久写入的 Published/Durable 区别和进程身份校验仍是实现要求。

## 7. 后续设计与验证要求

本次确认的是三平台统一产品策略，以下实施细节必须在写代码前具体化，并作为同一方案的实现审查内容：

1. 三平台统一的检测结果模型与 UI 获取途径：特别是 daemon 不可用、普通用户不能读取 root journal 时，由已有权限边界内的安装检查能力返回结果，TUI 不直接打开或写入受保护业务文件。
2. Windows 的最小操作记录和三个平台的显式接管协议：准确路径、owner/ACL、格式、原子提交点和再次中断行为。任何新增持久格式必须展示具体 schema 后审核，不将 Unix journal 生搬到 Windows。
3. 修复安装与全新安装的准确命令/安装脚本入口、删除清单及非交互授权方式。现有 `service reinstall` 只重注册的帮助和行为不能被悄悄扩大为清数据。
4. 落实 §1.1/§5 已确认的安装完整提交点与首次启动/Ready 分离：给出实际持久格式、服务启用策略及锁释放顺序，不再为未知中断状态补自动 source 恢复。未完成状态检测、正常首次启动和普通重启必须能同时满足本策略。

验收必须覆盖三个平台相同的用户可观察结果：

- 正常运行断电后可重新启动；正常 stopped/disabled 不误报，活跃安装仅报告进行中。
- 安装完整后端口冲突、配置错误、Ready 超时仅提示启动失败，重试启动不执行重装或恢复；要求启动却失败时不得报整体成功。
- 安装资源完整提交后、首次启动之前再次断电，重启仍识别为已完整安装；资源未验证或同步失败不能被提前标记完成。
- 确认中断才弹提示，取消后无安装/恢复/删除副作用，后台不弹桌面窗口。
- 修复安装前后用户配置、订阅、设置和既有日志保留；数据损坏时失败且不清空。
- 全新安装拒绝未确认和越界删除，只处理预览范围；其他实例、其他用户和迁移来源不受影响。
- 原安装及显式修复的每个关键中断窗口仍可被检测；不存在隐式 RecoverLocked 或 action replay。
- 修复连续两次中断后再次选择修复，仍保护原有业务数据和实例范围；选择关闭提示后没有后台修复、回滚或删除。
- 程序损坏时独立安装入口可处理；权限不足、凭据失败、记录损坏和 daemon 连接失败不误分类。
- 安全停止、程序/定义发布和真实 Ready 校验按平台隔离测试；真实系统服务只在授权的隔离 hosted 环境验证。

本轮只更新设计和计划状态，现有 Go、脚本、测试和未提交共享组实现均未修改。
