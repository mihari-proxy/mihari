# 三平台核心版本与更新设计

日期：2026-09-17；2026-09-19 按用户批准的范围复审重写。产品决定已确认，实现仍须通过最终验证；不表示已发布。决策见 [ADR 0005](../../adr/0005-core-version-and-source-policy.md)，范围取舍见[复审记录](../plans/2026-09-19-core-scope-reassessment.md)，完成证据见[执行计划](../plans/2026-09-17-core-version-and-update-plan.md)。

## 产品规则

| 场景 | 结果 |
| --- | --- |
| 在线安装、更新、切换通道 | 解析 MetaCubeX/mihomo 官方 stable 或 alpha 最新版，并固定本次制品 |
| 本地已有核心 | 不要求官方来源凭据或编译版本表；保留所在平台已有权限和文件身份保护 |
| 离线首次安装 | 可使用包内核心，不联网证明它是最新版 |
| 更新 Mihari 应用 | 保留已有核心及通道；核心由用户主动更新 |
| 常规更新失败 | 保留或恢复旧字节、原通道与原运行意图，返回失败 |
| 更新及回滚均失败 | 停止自动尝试，保留诊断和备份，阻止不确定核心启动 |
| daemon 强杀或机器断电 | 启动时检测未完成更新并阻断；不自动重放整笔事务 |
| 用户主动重装 | 重新取得更新前原通道的官方最新版，保留订阅和配置；验收成功才解除阻断 |

不增加任意版本、自定义来源或核心导入入口；不建设 Windows／非 root Unix 的完整持续执行检查体系。普通核心重启没有修复语义。首次安装沿用启动意图，已停止的核心更新或重装后保持停止。未能验证的未来版本仍可能不兼容，候选检查与回滚不等于兼容性保证。

## 为什么曾经只有 Unix root 被固定版本限制

Unix root 装配了 `TrustedExecution`，原版本通过 receipt 与编译表决定核心执行资格；Windows 使用普通安装器，没有注入相同执行能力。此次解除 Unix 的版本／官方来源准入耦合，保留其安全根、文件身份和执行生命周期检查。旧 receipt 不是新运行的来源证明；旧未完成 pair WAL 仍须按既有规则处理，不能直接删除绕过。

## 目标解析与候选准备

`internal/core` 统一安装与版本检查的目标规则。目标记录发布与资产 ID、通道、平台、版本、大小、更新时间和可选摘要。下载使用选定资产端点并在前后复查；发布 newer latest 不改变目标，资产变化或消失导致本次失败，不自动换通道或制品。

官方 SHA-256 存在时必须匹配；缺少摘要时允许官方 HTTPS 下载，向客户端返回 warning。下载超时、大小、重定向来源和解压边界继续生效。自行计算的哈希只用于本地完整性和身份比较，不冒充官方摘要。

准备阶段不停止旧核心。候选需通过目标版本和当前配置验证。Unix root 复用受保护执行路径；普通平台在候选校验与提交之间复查文件对象。配置 generation、目标核心身份及 revision 在提交前复查。

## 所有权与常规失败回滚

- `internal/runtime.Manager` 拥有一次操作、核心设置提交、冲突控制与结果诊断。客户端不写核心或业务文件。
- `internal/supervisor` 拥有停止、进程回收、试启动及健康验收，不写 settings 或更新记录。
- `internal/core` 负责固定角色的候选、旧核心备份、发布与回滚。普通平台的 `NewUpdateStore` 仅提供更新文件操作，不提供 Unix 的 `VerifiedCore` 执行能力。
- `internal/app` 装配运行时，并在既有停机安装事务中处理 Unix 迁移与离线包。

提交阶段停止旧进程，保存备份与最小中断证据，发布候选，按原运行意图试启动并验收，再保存核心通道和完成标记。备份保留到整体成功；配置、下载等前置失败不改旧核心。发布、启动或设置失败则恢复旧字节和核心设置，并按原意图验收旧核心。恢复失败保留两个原因和材料，停止自动重试。

完成标记确认后，后续清理失败是 warning，不将已成功提交反向回滚。持久阶段用来区分本次提交／补偿及启动阻断，不形成后台崩溃重放引擎。

## 中断与用户重装

活动记录位于数据根 `staging/core/update-journal.json`，固定事务材料位于 `staging/core/update/<transaction>/`。非终态记录阻止普通启动、版本探测和 mutation；有效记录下仍装配 daemon 的受限修复 owner 和本地认证控制面。诊断显示材料位置及重装指引。

`POST /v1/core/reinstall` 是本地协议的兼容新增入口，使用已有 mutation 元数据、revision、结果及错误 envelope，并通过 `core-reinstall` 能力公布。CLI 为 `mihari core reinstall`；TUI System 为 `Reinstall core`，需确认。它不复用“服务重装”，也不自动触发。

重装从未完成记录取得原通道和运行意图，重新解析该通道最新版；相同版本也重新下载。旧记录先归档在原材料目录，原备份不被新的清理删除。候选发布、设置保存及适用的启动验收完成前保持阻断；失败不能执行不确定旧核心，材料仍保留，可再次主动重装。

已损坏的恢复记录、权限不足或无法绑定现有配置须报告具体原因，不能猜测通道或删除标记。重装不是通用维修工具。Unix 既有核心无法完成启动配置验证时，只有现有配置仍能安全绑定，才保留受限修复 owner；新候选仍须重新验证配置。

## 安装器与离线包

Unix 安装器保留已识别目标数据；迁移按持有的源对象复制本地核心及核心通道，不将旧 receipt 当成来源授权。没有既有核心时使用已验证 AIO 包内核心；不再额外获取编译表中的 v1.19.30。发布锁文件只约束可复现离线包构建，仍予保留。

Windows AIO 仅在核心缺失时写入包内核心及其通道；应用升级不覆盖已有核心。用户配置、订阅和面板状态保持。

## 验证与交付边界

使用合成发布元数据、归档、fake core、隔离临时目录和既有原生测试设施，覆盖解析、摘要策略、文件变化、普通回滚、原通道、停止意图、中断阻断、重装失败与重试及本地控制入口。中断测试断言材料保留和阻断，不要求自动恢复旧事务。

最终需要相关集成、全仓测试、race、vet、lint、六目标 CGO-free 构建和 PR CI/bot review。真实核心、订阅与系统服务测试未授权。平台或权限受限的检查明确记录，不以交叉编译代替原生运行，不以部分测试通过声称完成。
