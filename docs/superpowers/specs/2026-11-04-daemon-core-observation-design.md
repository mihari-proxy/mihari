# Issue #364：核心状态观测与执行校验

状态：Q1–Q6 与最终方案已获用户确认，已授权实施、提交与创建指向 dev 的 PR。

已确认：初始观测在依赖该结果的状态服务开放前完成，设置超时并复用已有启动检测。

已确认：外部删除或替换文件后，允许继续展示上次确认的本地版本与可用性，直到相关生命周期操作重新检查；Mihari 自身操作及时更新观测。实际执行仍检查身份和权限，不静默重新接纳外部替换文件。

已确认：流式摘要可以纳入，但必须控制触发次数；普通状态轮询不执行摘要校验或版本探测，不新增每秒校验任务。

已确认：保持 Mihari 自身构建版本展示、在线更新检查以及安装/更新中的目标版本探测机制，本次不调整其行为。

## 问题与已确认事实

Ubuntu VM 的 daemon 在连接 TUI 时持续高 CPU。每秒状态轮询经 SetupRequired / LocalCore 进入 InstalledAvailable / DetectVersion，重复执行 OpenInstalledCore。Unix 实现的 Inspect、open 和 verify 多次整文件读取、计算摘要，并以 io.ReadAll 分配大对象。

核心版本来自 mihomo 自身的版本输出；整文件读取服务于执行前校验，不是提取版本所必需。运行中的进程与磁盘上的程序可以不同，不要求持续一致。既有文件身份与权限保护、未完成更新阻断规则继续适用于实际执行。

## 修改提案

1. Manager 持有仅在本次 daemon 生命周期内有效的本地核心观测结果，以原子发布的不可变值记录可用性与版本；不新增持久化数据或协议字段。
2. 复用启动装配已有的版本检测并增加 5 秒超时，以其本次内存状态初始化观测。安装、更新、回滚、重装及恢复发布各自已验证的结果，不增加后台探测。生命周期持有既有 mutation 所有权；legacy setup 的版本探测在取得所有权后重新检查观测身份，拒绝旧探测覆盖新安装。
3. 普通 GET /v1/status 和 GET /v1/core 读取已发布结果，不全量读取二进制、不执行版本命令。SetupRequired 保留重置未完成、端口待重启等现有规则；核心资源判定改为使用观测。
4. 运行状态继续来自 supervisor。磁盘文件的观测与当前进程状态分开，不把缓存的版本或 ready 当作执行授权。
5. 实际启动、配置验证、版本探测等真正执行路径保留已有校验；不修改 executionGate 的 admission 规则，不允许外部替换文件被悄悄重新接纳。
6. 附带优化：必须计算摘要时使用有界缓冲流式计算，替代只为摘要而进行的 io.ReadAll；需要原始字节的读取保持原用途。优化不能引入额外定时检查，也不能替代消除状态查询中的重复校验。

## 范围之外

- TUN 冲突扫描不属于当前主因修复。
- Mihari 自身版本展示、更新检查与安装/更新目标版本探测保持不变。

## 观测结果的既有消费者

- Setup 核心步骤以 localReady 显示缺失或可复用，以 localVersion 显示本地版本，并决定自动引导复用路径。
- System 核心更新检查优先使用运行记录中的 Version，缺失时使用 LocalVersion。
- app 的 endpoint restart 等待逻辑也使用 LocalReady 判断是否应等待核心；实施不能仅把这些字段当作界面文案。
