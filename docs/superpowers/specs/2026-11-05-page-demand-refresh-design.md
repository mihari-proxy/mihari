# Issue #367：按页面需求刷新 TUI 快照

状态：Q1–Q18 及整体方案已由用户确认，用户随后授权开始实现。#370 已合并，本文件是 #367 的实施依据。

## 已确认的背景与边界

- #370 已于 2026-11-05 合并到 dev，合并提交 fec11285。该轮完成系统展示观测复用及 F4 Performance。
- Issue 8 对应 #367：按页面需求刷新快照，并合并重复更新。#368 的凭据校验生命周期另行处理。
- 当前 Session 会按固定周期拉取所有 capability 支持的页面快照；当前页面不影响请求集合。根模型的状态事件另触发网络状态读取。
- 这轮需覆盖页面进入、重连、core 身份变化、用户刷新和 mutation 后的数据及时性。
- mihomo 的外部变化不能仅靠 Mihari 全局 revision 判断；仍需在有需求时探测。
- F2 全局诊断、流式数据、操作结果的顺序和可见性必须保持。
- 设计决定随访谈记录；未确认的方案不视作已批准需求。

## 已讨论的决策范围

- 页面需求何时生效：导航选中、进入内容、弹窗遮挡。
- 无消费者的页面快照是否完全暂停。
- 返回页面时旧快照的展示与刷新行为。
- 全局/Overview/当前页面的具体资源需求与刷新节奏。
- 进入、重连、core 变化、主动刷新和操作完成的刷新与失效规则。
- 同轮合并、无变化抑制、队列与流式数据顺序边界。
- 回归测试与 VM 对照方案。


## 已确认决定：第一轮

- Q1：导航选中页面即构成页面需求；不要求先 Enter 进入内容焦点。
- Q2：某份页面快照没有任何页面或全局消费者时，停止其周期查询。
- Q3：同一 daemon、同一 core 身份下返回页面，先保留旧快照，标示正在刷新，并立即请求更新。旧显示不自动等同操作依据。

## 已确认决定：第二轮

- Q4：按已核实的页面需求表启停专用查询；多个消费者共享相同资源的查询。全局消费者保留。
- Q5：F2、F4、确认弹窗遮挡时，选中页面继续刷新快照；自动测速保留已有的弹窗暂停规则。
- Q6：返回页面请求刷新期间，旧列表可浏览；依赖候选有效性的操作等待本次刷新成功后恢复，继续遵守既有操作门禁。刷新失败保留列表、展示失败状态并允许重试；不冻结无关操作。

## 全局 revision 的事实边界

不能仅因 Mihari 全局 revision 未变，就永久跳过快照查询：

- Subscriptions：下载/解析等准备失败可直接更新 catalog.LastError，不递增全局 revision。
- Core：LocalReady/LocalVersion 来自独立观测，部分发布路径不递增 revision。
- Preferences：正常保存会递增 revision，但当前 GET 的偏好值和 revision 分两次读取，可能捕获旧值和新 revision。
- mihomo 节点/路由/provider 的外部变化也不由 Mihari revision 完整描述。

本轮不借刷新优化扩大修改这些资源的持久化或协议边界。具体周期已由 Q7 确认。


## 已确认决定：第三轮

- Q7：Status/Core 每 1 秒；当前页面专用快照每 1 秒；Subscriptions 在 Overview/Subscriptions 每 1 秒，其他页每 5 秒；Preferences 平时每 5 秒，打开 F4 立即刷新且打开期间每 1 秒。Service、F2 诊断、四类 streams 保持现有节奏。切页、主动刷新、相关操作完成时立即刷新，不等周期。先不增加可调参数；以上是调度节奏，不承诺慢请求仍能精确每秒完成。
- Q8：普通重复刷新可共享等价在途查询；操作前开始的查询不能确认操作后状态，其陈旧结果不得发布，操作完成后补查。同类后置刷新请求合并，不排成长队。
- Q9：daemon/core 身份改变，清除受影响实时列表并重新加载；日志、连接历史、F2 诊断和操作历史保留。仅短暂断线且身份未变时，保留旧显示并标断线，重连立即刷新。


## 已确认决定：第四轮

- Q10：业务内容相同则跳过重复整理及页面同步；刷新成功、有效性确认和新的 warnings/diagnostics 独立处理，不能因业务内容相同而丢失。
- Q11：离页不取消已发起的业务操作，结果归属和诊断保持。操作后仍有消费者的资源立即刷新；没有消费者的资源标记失效，回页再查。这是 Q7 操作完成立即刷新的无消费者特例。
- Q12：daemon 健康而单项资源查询失败时，保留旧显示并标失败，按该资源正常周期重试；不紧密循环、不阻塞其他资源。daemon 连接失败沿用现有重连退避。
- Q13：对已经就绪的快照成组交给 UI，减少重复同步；不为凑齐一批等待慢资源。日志、连接历史、诊断与操作结果维持原有顺序和完整性，不覆盖丢弃。


## 已确认决定：第五轮

- Q14：每次普通快照刷新设置 5 秒总预算，包括附带诊断读取。同一资源最多一个在途查询；资源独立调度，慢请求不阻塞其他资源或 Status 心跳。超时按 Q12 处理。业务 mutation、下载、持续 streams 不使用该快照预算。
- Q15：只读查询失去全部消费者时取消，回页再刷新；迟到的失效结果不能覆盖新状态。其他消费者仍需要的请求、全局请求和业务操作不取消。

## 生命周期事实

当前 Session 无逻辑快照总预算；client 单次 HTTP 超时为 60 秒，附带的 warnings/diagnostic 解析还可能串行发送多次 HTTP 请求。原快照轮询和 stream 监督选择循环同步串行执行，慢快照会阻塞后续 Status、资源和 stream 错误处理；已有 stream 生产与 dispatch 则独立运行。这是本轮独立资源调度及快照总预算的依据。


## 已确认决定：第六轮

- Q16：daemon 健康检查成功后显示已连接，并启动流式接收；普通资源分别加载，不等整轮快照。尚未取得有效数据的依赖操作保持禁用。
- Q16 补充（用户明确要求）：首轮 fetching 必须可感知，不能只展示空白 TUI 或把默认零值当真实结果。普通快照区分首次加载、已成功但为空、加载失败；已有同身份旧数据时沿用 Q3 的显示并标示刷新中。具体视图适配以现有样式为基础；已核实的状态模型缺口见首轮展示部分。
- Q17：不增加“只保留最新不同快照”的丢弃规则。保留不同快照及身份/能力/失效/恢复事件先后，仅合并共享视图同步，相同内容按 Q10 跳过重建。

## 实施边界与验收方案

- 只调整 TUI 的快照需求、资源调度、合并/分发及相关加载展示；共享 Session/root/页面已有的重复普通状态读取。独立版本检查、下载、对话框专用任务、业务 mutation 规则保持现有边界。
- 不新增依赖、持久参数或公开 CLI/JSON 契约；不改 #368 的凭据生命周期。
- Status/core/消费者变化、startup network Applying、endpoint restart、重新连接沿用现有语义，并对新 worker 明确 cancel/join 所有者；logger 在生产者结束后关闭。
- 相等短路不跳过刷新有效性、revision/owner 等操作元数据或新 warning/diagnostic；批处理不创造跨队列总顺序承诺。
- 确定性测试覆盖各页面请求集合/周期、首轮加载与空/失败区分、慢资源不阻塞、请求合并、操作前后交错、离页取消、迟到结果、身份替换、重连、后台操作、诊断和流式历史顺序，以及退出 join。
- 同 VM、同客户端数/终端尺寸/页面做至少 60 秒对照，记录请求数及 TUI/daemon/core CPU。沿用之前不强求 CPU 减半的验收要求，实际报告限制及 #368 留存成本。


## 首轮展示的核实结果

多个页面目前缺少“尚未加载”状态：Proxies、Rules/Providers、Subscriptions、WebGUI 会直接进入空态；Overview 和状态栏存在默认零值或隐藏字段。System 部分资源已有 loaded flags，可复用现有 Loading/Fetching 样式。

Q18 已确认：各卡片/列表独立展示首轮加载、成功空、首轮失败；全局状态栏与 Overview 不把尚无样本显示为确认的零值。普通刷新有旧值时继续显示旧值并标刷新。streams 当前没有统一的上游 ready 事件，首样本前只能如实显示等待数据；本地 WebSocket 握手成功不能证明 mihomo 上游已就绪，也不能据此显示确认的零连接。


## 已确认决定：第七轮

- Q18：卡片/列表首次加载使用现有 Loading/Fetching 与 spinner 样式，数据逐块填入；成功空响应后才展示空态。首次失败展示失败概要并按周期重试。已有旧值时保留内容并标刷新中。流式监控首样本前显示等待数据/—，不假报确认的 0。
- 加载状态按资源独立展示；顶栏可以同时显示 daemon 已连接。不新增骨架屏或公开流式 ready 协议；已有连接状态不能冒充上游样本。
