## 调查事实

- root 的 SystemProxy → Tun → Egress 是顺序请求，三者实际观测均持 maintenance 锁。仅合并重叠请求不能消除单客户端不重叠的周期查询。
- Linux TUN 状态查询会枚举网卡、扫描 /proc 中各进程的 comm，并对命中进程取 stat/exe。构造自身身份时，还会从 /proc/net/tcp[6] 查 controller socket inode，再遍历进程及 fd 链接反查占用 PID。
- 当前有 controller 地址和 lookup 后端时就执行端口归属反查，没有先按其他已知身份判断是否需要兜底。其他 mihomo 进程属于展示证据，TUN 适配器证据才是 enable 的冲突门禁，不能混为一个开关。
- TUI 常规服务状态由进程内 ServiceController 查询，未经过 daemon 服务状态端点；daemon 服务缓存无法替代该处优化。系统代理观测也可能绑定用户/session。
- 每类观测的新采集都会重新读取所需 controller 配置，不在观测缓存内再嵌套一个已完成配置缓存，避免累计延长数据年龄或让主动刷新间接复用旧配置。
- 完整业务 DTO 还包含当前设置、revision、期望状态、运行身份与诊断。应复用底层观测，不能连当前业务字段一起变旧。
- TUN 部分采集失败被现有 helper 转为 nil conflict，最终 DTO 没有 error 不代表采集成功；缓存资格必须在仍保有原始 error 的边界判断。

## F4 Performance 设置

在现有全局 F4 目录加入独立的 Performance 分类，不为每个页面分别保存一套性能选项。

1. Controller owner detection：默认关闭，仅控制普通状态查询中的 controller 端口归属反查（Q3=A、Q4）。
   - 不关闭其他 mihomo 枚举或 TUN 网卡冲突检测。
   - 实际操作前按需要执行最新的端口归属检查。
   - 缺少端口归属证据不构成“属于自身”或“没有冲突”的证明。
2. Observation reuse (seconds)：整数，默认 3，范围 0–5（Q1、Q6）。
   - 成功完成时开始计算复用年龄（Q14）。
   - 0 关闭跨请求的结果缓存，但仍允许合并同时发生的等价查询。
   - 这是复用期限，不是新增后台定时刷新任务，也不是外部变化必定被发现的时限。

两个设置均为实例级持久偏好，多个客户端遵守同一策略（Q5）。沿用现有 preferences/tui.json 与 /v1/preferences/tui，增加明确的可选 Performance 结构；不迁移或重命名旧文件，不把状态探测策略写入 mihari.yaml。

F4 仍一次 Save 提交全部草稿，包括 Proxies 与 Performance；由 daemon 单写入者、统一 mutation 与 IfRevision 完成单文件保存（Q16）。保存成功立即生效，不要求重启；其他客户端经现有偏好轮询同步。Cancel 不写入，冲突不自动覆盖其他人的设置。

默认值尽量不写入持久文件。b48ad7e 的 preferences.Open 和 Unix 安装迁移解码器都会拒绝未知字段：写入新 Performance 字段后，降级到该版本前必须恢复默认并省略字段，或显式移除字段。用户已接受兼容影响；不泛称所有历史版本的读取行为都相同。

## 观测复用语义

- 覆盖 TUN、出口网卡、系统代理、OS 服务状态（Q8），分别在实际执行观测的所有者处复用。服务状态在 TUI 本地共享 controller 路径中处理；daemon 管理其网络观测。
- 只缓存成功观测；同一次执行的失败可以共享，后续请求允许重试（Q11）。不将失败缓存为“没有冲突”，不顺带改变实际操作遇到探测失败时的既有放行/拒绝策略。
- 未过期普通查询可复用；过期查询等待新探测，不返回过期值（Q7）。
- 主动刷新不使用已完成缓存，但可加入仍有效的等价在途探测（Q12、Q13）。
- 单个等待者取消只停止其等待；仍有其他等待者则继续。全部等待者离开、执行所有者退出或超时，才取消共享执行（Q10）。
- 共享探测等待上限为 5 秒（Q15）。可取消步骤及时停止；无法立即中断的本机调用结束后丢弃结果，不允许同类任务无限堆积。
- 设置、core epoch、运行身份、系统代理主体/session 必须进入相应的观测身份和失效规则，不能跨不同实例或用户主体复用。
- Mihari 启停 TUN、调整出口/代理、重启 core、修改 Performance、重置数据等相关操作立即使对应观测失效，不等待期限（Q9）。操作失败但可能改变环境时也失效。
- 操作前开始的旧探测不得覆盖新状态；新请求不能加入已失效执行。实际操作前门禁、回滚前像与执行后确认始终新鲜，不使用普通展示缓存。

## 偏好保存成功边界（Q17）

用户最终确认：文件替换与父目录同步全部完成，才向用户报告保存成功并发布新偏好。保存失败使用旧值，页面保留草稿，由用户手动再次 Save；不采用“替换成功就直接使用新值并只报 warning”的提案。

当前实现的缺陷：preferences.Update 使用 AtomicWrite 的 error-only 接口。replace 成功后目录同步失败也返回 error，但磁盘已经是新文件，内存和 revision 仍是旧值。本轮需覆盖该直接相关路径。

目标规则：

1. 校验并保留最后一次确认的旧偏好，以及原文件是否存在和用于恢复的旧内容。
2. 候选内容写临时文件、同步文件、原子替换目标、同步父目录。
3. 完整成功后，才发布内存、推进 revision、更新 Performance 策略并使相关观测失效。
4. 替换前失败：旧文件和内存保持；错误保留，草稿保留。
5. 替换后同步失败：撤回本次文件修改，恢复此前确认的旧文件状态；原文件不存在时应恢复缺失状态。内存和 revision 不发布新偏好。
6. 手动重试使用新 operation ID，并继续遵守 IfRevision；不能命中上次失败执行的去重结果，也不能无条件覆盖并发修改。
7. 若撤回本身遇到存储故障，必须报告保存与撤回的实际错误，保留旧内存和草稿；不能虚报磁盘已恢复或断电持久性已保证。这是存储操作的物理失败边界，不承诺磁盘损坏时仍可保证撤回成功。
8. 不增加永久后台补同步或自动重提设置任务；未批准将自动重试变成用户保存规则。

这次偏好保存边界仅作用于该单文件保存用例，不借机更改现有 Settings 已提交 warning 的通用语义。
